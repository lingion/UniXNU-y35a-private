## Direct comparison

The three 69,632-byte captures differ only at:

- `0x10..0x14`: the probe's CNTVCT witness
- `0x10008..0x1000f`: the boot shim's `Y35AXNU2` handoff stamp

The record region and the remaining staged bytes are byte-identical across all three captures. This proves that the probe executed three times and that the handoff stamp tracks the preceding boot generation. It does not prove that the symbol-addressed records are runtime-mutated XNU state.

## Marker placement fact

`native-phase-markers.patch` writes `record[5]` at `phystokv(BootArgs->topOfKernelData + 0x800)`. The readback manifest stages that region as the `early-fault-record` beginning at raw offset `0x40`, so the marker slot would be raw offset `0x68` when the phase kernel reaches the marker. The r7 probe uses the legacy kernel generation and therefore cannot answer whether the phase markers executed.

## Current conclusion

The capture chain is live. The remaining unresolved question is the address and ownership of the runtime state, not whether the probe binary ran. Do not use identical r7 records as proof that XNU did not run, and do not use the handoff stamp as proof that XNU reached a panic header.

## Next offline test

1. Build or inspect a phase-kernel probe whose manifest explicitly records the phase kernel SHA and the marker raw offset.
2. Verify the phase kernel binary contains the marker stores and that the target page is writable under the boot layout.
3. Add a distinct entry marker in the assembly handoff record, separate from the XNU C marker, so the next capture distinguishes shim entry, XNU entry, and post-`arm_vm_init` state.
4. Run the focused offline tests before requesting another device boot.
